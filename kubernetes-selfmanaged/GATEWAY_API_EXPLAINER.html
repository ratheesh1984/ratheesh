1. What is Kubernetes Gateway API?

Gateway API is a set of Kubernetes resources that control how network traffic enters your cluster and reaches your applications. It was created by the Kubernetes networking community and is now the official successor to the older Ingress resource.

Think of it as a smart traffic director sitting at the edge of your cluster. Every HTTP request from the internet passes through it, and it decides which application to send the request to based on rules you define.

Simple analogy: Imagine a hotel reception desk. Guests (HTTP requests) arrive at the front door (Gateway). The receptionist (NGINX Gateway Fabric controller) looks up the room directory (HTTPRoute rules) and sends each guest to the right room (your app pod).

Gateway API is not built into Kubernetes by default. It is installed as Custom Resource Definitions (CRDs) — extra object types added on top of Kubernetes — and then a controller (in our case NGINX Gateway Fabric) watches those objects and programs the actual NGINX proxy.

2. Gateway API vs Ingress — Why the Change?

The older Ingress resource (which this cluster already uses on port 30080) was designed years ago and has limitations. Gateway API was built to fix them.

Feature Ingress (old) Gateway API (new)
Kubernetes version Stable since v1.0 Stable since v1.28 (2023)
Resource type Single Ingress object 3 separate objects: GatewayClass, Gateway, HTTPRoute
Who controls what One resource mixes infrastructure + routing Clear separation: infra team owns Gateway, app team owns HTTPRoute
Cross-namespace routing Not supported Built-in — route to services in other namespaces
Traffic splitting Limited / annotation-based hacks Native (canary, A/B testing with weights)
Header / path matching Basic Advanced (regex, header matching, query params)
Can they coexist? ✅ Yes — both run in parallel without conflict
In this cluster, Ingress (ingress-nginx) still runs on port 30080 and Gateway API (NGINX Gateway Fabric) runs on port 31417. They handle traffic independently.

3. The 3 Gateway API Resources Explained

Gateway API splits routing into three distinct Kubernetes objects. Each has a specific job.

① GatewayClass

What it is: Declares which software (controller) will handle the gateways.
Who creates it: The cluster infrastructure team (or the controller itself).
Scope: Cluster-wide (no namespace — one per controller type). 
# 06-gatewayclass.yaml
apiVersion: gateway.networking.k8s.io/v1
kind: GatewayClass
metadata:
  name: nginx                          # name used by Gateway resources
spec:
  controllerName: gateway.nginx.org/nginx-gateway-controller

Analogy: This is like choosing which airline operates the airport. You're saying "all Gateways of class nginx are managed by NGINX Gateway Fabric."

② Gateway

What it is: Defines a network entry point — which port and protocol to listen on.
Who creates it: The cluster/platform team.
Scope: Namespaced (lives in a specific namespace). 
# 07-gateway.yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: tomcat-gateway
  namespace: tomcat-app
spec:
  gatewayClassName: nginx              # links to the GatewayClass above
  listeners:
    - name: http
      protocol: HTTP
      port: 80
      allowedRoutes:
        namespaces:
          from: Same                   # only HTTPRoutes from tomcat-app namespace

Analogy: This is the airport terminal — it defines gate 80 is open for HTTP flights. Only routes from the same terminal (namespace) are allowed to board.

③ HTTPRoute

What it is: The actual routing rules — which URL paths go to which service.
Who creates it: The application team.
Scope: Namespaced (lives with the app). 
# 08-httproute.yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: tomcat-route
  namespace: tomcat-app
spec:
  parentRefs:
    - name: tomcat-gateway             # attach to the Gateway above
      namespace: tomcat-app
  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /                   # match ALL paths
      backendRefs:
        - name: tomcat-service         # send traffic to this ClusterIP service
          port: 80

Analogy: This is the flight manifest — it says "all passengers (requests) on gate 80 with any destination (/) go to the Tomcat boarding gate (tomcat-service:80)."

4. How Traffic Flows Through Gateway API

Complete request journey

Browser: http://20.127.130.235:31417/
↓
Azure NSG: AllowNodePorts (30000–32767) ✅
k8s-master: NodePort 31417 → nginx-gateway Service (LoadBalancer)
↓
kube-proxy DNAT: routes to NGINX Gateway Fabric pod (same node)
nginx-gateway-fabric pod (on k8s-master)
↓
Reads HTTPRoute rules → matches path "/" → forward to tomcat-service:80
tomcat-service (ClusterIP 10.98.213.16:80) — internal hop
↓
Calico VXLAN tunnel (UDP 4789) — cross-node overlay to worker
tomcat pod on k8s-worker :8080 → 200 OK
Key point: The tomcat-service (ClusterIP) is still used for the internal hop from the gateway pod to the tomcat pod. NodePort is only needed at the very edge because this is a bare kubeadm cluster — no Azure LoadBalancer is attached.

Component responsibilities

Component Where it runs Job
nginx-gateway pod k8s-master (pinned) Reads GatewayClass, Gateway, HTTPRoute objects and programs NGINX proxy
nginx-gateway Service nginx-gateway namespace Exposes the controller pod via NodePort 31417 (LoadBalancer type, but no cloud LB)
tomcat-service tomcat-app namespace Internal ClusterIP — routes from gateway pod to tomcat pods

6. Every Issue We Hit and How We Fixed It

Issue 1 — GatewayClass had a namespace field Bug Fixed

Problem: GatewayClass is a cluster-scoped resource in Kubernetes — it does not belong to any namespace (like Node or PersistentVolume). The original YAML had namespace: tomcat-app which would be silently ignored or cause errors.

Before (wrong)After (correct)
metadata:
  name: nginx
  namespace: tomcat-app  ❌
 
metadata:
  name: nginx
  # no namespace — cluster-scoped ✅

Issue 2 — Wrong controller name Bug Fixed

Problem: The controllerName in GatewayClass was nginx.org/nginx-gateway-controller. The correct name for NGINX Gateway Fabric is gateway.nginx.org/nginx-gateway-controller. The controller only picks up GatewayClass objects whose controllerName matches exactly — a wrong name means the controller ignores all your Gateways.

Before (wrong)After (correct)
nginx.org/nginx-gateway-controller ❌ gateway.nginx.org/nginx-gateway-controller ✅

Issue 3 — NGINX Gateway Fabric CRDs not installed first Bug Fixed

Problem: NGINX Gateway Fabric v1.4.0 requires its own custom CRDs (NginxGateway, ClientSettingsPolicy, etc.) to be installed before the main deploy.yaml. The original script only installed the standard Gateway API CRDs but skipped the NGINX-specific CRDs.

Error seen: 

no matches for kind "NginxGateway" in version "gateway.nginx.org/v1alpha1"
ensure CRDs are installed first

Fix: Added a CRD install step before the main deploy:

# Step 1 — standard Gateway API CRDs
kubectl apply -f https://github.com/kubernetes-sigs/gateway-api/releases/download/v1.1.0/standard-install.yaml

# Step 2 — NGINX Gateway Fabric specific CRDs  ← new step added
kubectl apply -f https://raw.githubusercontent.com/nginxinc/nginx-gateway-fabric/v1.4.0/deploy/crds.yaml

# Step 3 — NGINX Gateway Fabric controller
kubectl apply -f https://raw.githubusercontent.com/nginxinc/nginx-gateway-fabric/v1.4.0/deploy/default/deploy.yaml

Issue 4 — Conflicting GatewayClass / immutable controllerName Bug Fixed

Problem: A GatewayClass named nginx already existed on the cluster from a previous attempt (with the wrong controllerName). Kubernetes does not allow you to change spec.controllerName on an existing GatewayClass — it is an immutable field. 

GatewayClass.gateway.networking.k8s.io "nginx" is invalid:
  spec.controllerName: Invalid value: "string": Value is immutable

Fix: Delete the old GatewayClass and let the deploy.yaml recreate it with the correct controller name. 

kubectl delete gatewayclass nginx --ignore-not-found
# then re-apply deploy.yaml — it creates a fresh one with the right controllerName

Issue 5 — Conflicting Gateway in the default namespace Bug Fixed

Problem: NGINX Gateway Fabric v1.4.0's deploy.yaml automatically creates a sample Gateway object called nginx-gateway in the default namespace. This Gateway was already accepted and owned port 80. When our tomcat-gateway in tomcat-app tried to claim the same port, the controller rejected it with: 

The resource is ignored due to a conflicting Gateway resource
Reason: GatewayConflict

Fix: Delete the auto-created default Gateway so ours can take over. 

kubectl -n default delete gateway nginx-gateway

After deletion, tomcat-gateway immediately became Programmed: True.

Issue 6 — Invalid wildcard hostname "*" in HTTPRoute Bug Fixed

Problem: Gateway API v1 does not accept a bare * as a hostname. The spec requires either a valid domain name (e.g. myapp.example.com) or a wildcard subdomain (e.g. *.example.com). A lone * is invalid. 

The HTTPRoute "tomcat-route" is invalid:
  spec.hostnames[0]: Invalid value: "*":
  should match '^(\*\.)?[a-z0-9]([-a-z0-9]*[a-z0-9])?...'

Fix: Remove the hostnames field entirely. When omitted, the HTTPRoute matches all hostnames — which is exactly what we want.

Before (invalid)After (correct)
hostnames:
  - "*"    ❌
 
# hostnames omitted = match all ✅

Issue 7 — nginx-gateway pod running on worker, traffic enters master Bug Fixed

Problem: The nginx-gateway pod was scheduled on k8s-worker (which has no public IP). External traffic from your browser hits the master's public IP 20.127.130.235:31417, gets DNAT'd across nodes to the worker pod, but the return path was unreliable — causing the browser timeout you saw.

This is the same root cause documented in DEPLOYMENT_GUIDE.md for the ingress-nginx controller earlier.

Fix: Pin the nginx-gateway pod to the master node using nodeSelector + a toleration for the control-plane taint (the taint prevents normal pods scheduling on the master by default). 

kubectl -n nginx-gateway patch deployment nginx-gateway --patch \
  '{"spec":{"template":{"spec":{
    "tolerations":[{"key":"node-role.kubernetes.io/control-plane",
                  "operator":"Exists","effect":"NoSchedule"}],
    "nodeSelector":{"kubernetes.io/hostname":"k8s-master"}
  }}}}'
BeforeAfter
Pod location k8s-worker (no public IP) ❌ k8s-master (public IP 20.127.130.235) ✅
Browser result Connection timed out ❌ Tomcat app loads ✅
